# 오류 분석

320 로트 블라인드 평가에서 정답과 어긋난 31건을 유형별로 분류하고,
각각을 **설계 의도인지 / 조치했는지 / 아직 못 고쳤는지**로 나눴다.

출처: `validation/evaluation.json` — 320 로트, 정확 일치 289, 기권 3.
판정 경로는 `validation/ground_truth.csv`를 읽지 않는다(`tests/test_architecture.py`가 강제).

---

## 요약

| 유형 | 건수 | 분류 |
|---|---|---|
| ACI skip-lot으로 ΔCD 계산 불가 (S4→S0, S5→S0) | 26 | **설계 의도** |
| monitor wafer 감시 주기 부족 (S5→기권) | 3 | **조치 완료** |
| 레티클 이상 초기 미검출 (S3→S0) | 2 | **미해결** |
| **계측 drift를 Etch로 오귀속** | **0** | — |

마지막 줄이 이 프로젝트의 대표 지표다. 오귀속은 정상 챔버의 recipe를 건드리게 만드는
가장 비싼 실수인데, 320 로트에서 한 건도 없었다.

---

## 1. ACI skip-lot — 설계 의도 (26건)

**증상** — Etch 챔버 이상 26건 중 13건, 계측 drift 24건 중 13건이 `정상`으로 나왔다.

**원인** — 해당 로트들은 skip-lot sampling으로 ACI를 측정하지 않았다.
ΔCD = ACI CD − ADI CD 이므로 ACI가 없으면 계산 자체가 불가능하다.

**판단** — 고치지 않았다. 없는 측정을 추정으로 메우면 그 순간 이 에이전트의 전제가 무너진다.
`cd-signature` 스킬의 DoD에 "ACI 미측정 로트에서 ΔCD를 추정하지 않았다"를 명시했고,
화면에도 `ACI skip — etch bias 계산 불가`로 표시된다.

**남는 한계** — 검출률 지표를 볼 때 분모를 전체 로트가 아니라
**ACI 측정 로트**로 잡아야 한다. Etch 13/13, 계측 8/11이 실제 판정 가능 구간의 성적이다.

## 2. monitor wafer 감시 주기 — 조치 완료 (3건)

**증상** — 계측 drift 3건에서 원인을 지목하지 못하고 `판정 보류`로 빠졌다.

**원인** — monitor wafer 점검이 주 2회다. 이상이 시작된 날에는 가장 최근 감시 데이터가
이미 2일 이상 묵어 있었다. 그 상태에서 "계측은 정상"이라고 단정할 근거가 없었다.

**조치** — 게이트에 `metrology_evidence_fresh` 조건을 추가했다.
감시 데이터가 오래됐으면 Etch 귀속을 허용하지 않는다.

**재검증** — 이 조건을 넣은 뒤에도 계측 drift → Etch 오귀속은 0건을 유지했다.
보류 3건은 **오답이 아니라 근거 부족을 근거 부족이라고 말한 결과**다.

**판단** — 감시 주기를 일 단위로 올리면 사라질 보류다.
그러나 주기를 임의로 바꾸면 데이터가 현업 관행에서 멀어지므로 그대로 두고,
**샘플링 설계가 판정 능력을 어떻게 제약하는지를 보여주는 사례**로 남겼다.

---

## 3. 레티클 이상 초기 미검출 — 미해결 (2건)

**증상** — 레티클 CD 오차 18건 중 2건을 `정상`으로 판정했다.
둘 다 이상이 막 시작된 시점의 로트다.

**원인** — 이 시점의 레티클 반복 성분이 아직 관리 한계 아래에 있었다.
현재 판정은 **로트별 단발 판정**이라, "아직 한계 안이지만 계속 같은 방향으로 흐르고 있다"는
정보를 쓰지 못한다.

**조치** — **아직 못 고쳤다.**
한계를 낮추면 정상 204건에서 오경보가 생긴다. 실제로 한계를 낮춰보면 오경보가 먼저 늘어난다.
필요한 것은 임계값 조정이 아니라 **누적합(CUSUM) 같은 순차 검정**이다.
지금 데이터로 구현 가능하지만 이번 범위에서 제외했다.

**남는 한계** — 검출 지연은 원리적으로 남는다.
"이상을 놓치지 않는다"가 아니라 **"이상이 자란 뒤에는 반드시 잡는다"**가 현재의 정확한 주장이다.

## 4. 데이터·정의상의 한계 (판정 오류는 아님)

| 항목 | 내용 | 대응 |
|---|---|---|
| 웨이퍼당 41점 | 모던 CD-SEM 실측 범위(13~36점) 상단을 넘는다 | 루틴 모니터링이 아닌 characterization급 플랜임을 명시 |
| TMU에서 TIS 항 제외 | TIS는 0°/180° 회전으로 정의되는 오버레이 전용 항 | 산출값을 **실제 TMU의 하한**으로 표기 |
| seasoning 거동 단순화 | 실제는 PM 직후 급변 → 안정화 → 완만한 drift의 3단계 | 선형 drift + PM 리셋으로 단순화했음을 명시 |
| 단일 원인 가정 | 실제 이상은 복합 원인이 흔하다 | 이 데이터로는 복합 원인 판정력을 검증할 수 없음 |

## 5. 오류 분석에서 바뀐 설계

| 발견 | 반영된 곳 |
|---|---|
| 묵은 감시 데이터로 "계측 정상"을 단정하면 안 된다 | 게이트 `metrology_evidence_fresh` |
| 계측 불확도가 크면 공정 판단 자체가 불가능하다 | 게이트 `tmu_within_budget` (예산 20%) |
| ACI 없는 로트를 추정으로 메우면 안 된다 | `cd-signature` DoD |
| 설비 이벤트가 겹친다고 원인이 확정되지 않는다 | `cause-attribution` DoD, 도구 응답 note |

## 6. 아직 하지 못한 검증

- **현업 판정 이력과의 대조** — 라벨을 직접 정의했으므로 이 결과는 진단 정확도가 아니라
  **기준대로 일관되게 동작하는지를 보는 재현성 지표**로 읽어야 한다.
  실무에서는 현업이 판정한 이력 데이터를 정답으로 두어야 한다.
- **주입 신호 크기의 타당성** — 크게 넣으면 판정이 쉬워져 의미가 없고,
  작게 넣으면 검증이 불안정해진다. 현업 담당자 검토를 받지 못했다.
- **LLM planner 평가** — 하네스(`validation/planner_eval.py`)는 완성했으나
  실제 모델 실행 결과는 아직 없다. 실행 방법은 README 참조.
